Dynamic boundaries

The four switchable boundaries around everything the cache does only to watch itself: where their code sits, who may switch them, and what a switch cannot change.

What this view is

Chapter 9 proposes dynamic boundaries: the parts of a system that only observe it, switched on and off while it runs, at no cost while off. In the cache there are four. This view is for the people who run the cache and the people who audit it: what each boundary watches, where its code sits, who may switch it, and what a switch is checked to leave unchanged. It is generated from clause N-12's formal statement, the program's sites, the build's checks and the image's own code.

While a boundary is off, each of its sites is one instruction that does nothing. Switching it on rewrites those instructions into branches to code kept out of line, and switching it off rewrites them back. The image has 40 sites; none is in a function the build inlines, so each appears once in the machine code. On two cores each core keeps its own time profile; the counters and sizes are shared.

What each boundary observes, and how each switcher is reached, are written by hand (BOUNDARY_WHAT, SWITCHERS, from N-12 and cache/control.py), as are the names of the allowed addresses; the write sets, sites, switchers and addresses themselves are generated from the intent and the program.

The build checks that no other function switches a boundary: "only ['ctl_execute', 'main', 'serve0'] switch boundaries". The control port accepts connections only from the addresses listed for the board under [control] in the intent: for the EC2 image, 172.31.7.144 (the bench helper) and 10.0.2.2 (QEMU's host, for the tests). A hostname there is resolved when the image is built, since the image has no DNS. A connection from anywhere else gets a reset. Access is by source address alone: the port has no password and no encryption (N-13).

Switching the log on also needs a log disk, found at boot (N-14). Without one, or where the firmware would not make the code writable, a switch answers ERROR and the boundary stays as it was.

What a switch is checked to leave unchanged

The checker never knows whether a boundary is on: it treats every site as on or off, independently, each time it runs. So every proof of every other clause holds for every setting of every boundary at every moment. The build adds three checks that make switching change nothing but the boundary's own counters (48 in all, every one passed):

  • Each site writes only its boundary's regions, including through anything it calls, and allocates and frees nothing: 40 checks, one per site. A site may not contain a return, a break, an allocation or a free at all.
  • Nothing outside a site reads what a site computed: 6 checks, one per function with sites that compute values (mc_alloc, tcp_send, tcp_output, tcp_poll, serve_pass, serve0). While a boundary is off, those values hold anything.
  • The boundaries are the declared ones, and only the three functions above switch them: 2 checks over the whole program.

These are checked by the build over the program's structure (build.py), not by the solver; the evidence records them as 48 obligations of kind "boundary" under N-12. The planted defects aimed at them were refused:

How a switch happens in the machine

The image carries a table of its 40 sites, sixteen bytes each: the boundary, the site's place in the code, and the branch that switches it on. A switch runs the patcher below. For each site of the boundary it writes either the branch or the no-op, cleans that line of the data cache and invalidates it in the instruction cache, and it ends with a barrier, so the core runs the new code from its next instruction. The cost plane charges each switch with the whole walk, 1,034 instructions, to the function that switches.

The patcher is 34 instructions, written by hand and trusted, like the boot code: no proof covers it, and translation validation treats a switch as a call to it. The code around the sites is checked against LLVM twice, once with every site off and once with every site on. While one core switches, the other may be running the code being rewritten. Arm's architecture allows a no-op and a branch to be exchanged while another core executes them, and the proofs already allow each site to be in either state; the build does not check this, and it rests on that rule of the architecture.

The price: writable code

Rewriting code means the code must be writable. On UEFI the firmware maps an image's code read-only, so at boot an image with dynamic boundaries asks the firmware to make its own code pages writable, and gives up that protection for as long as it runs. If the firmware refuses, every boundary stays as it was booted, and switching one answers ERROR (N-12). A first attempt edited the firmware's page tables directly; it worked under QEMU's firmware and hung on EC2's (Appendix A, step 18).

What the protection still guarded is narrow. The program's own writes are proved to stay inside its regions, which do not include its code, and only the patcher writes code. It guarded against what the proofs do not cover: the trusted code, the firmware and the devices (see Trust boundaries). An image built without dynamic boundaries keeps its code read-only.

What off costs, measured

Measured On EC2 the same commit was built three ways and run alternately: the observing code compiled out, present and switched off, and all switched on. Pipelined, where the server is the limit, switched off ran 2–4% ahead of compiled out, and all on level with it; small requests varied more between rounds than between images (Appendix A, step 18). With the access log on, throughput was level with it off; in one four-minute run 87% of records reached the disk and 13% were dropped, the disk being the limit (step 22).
