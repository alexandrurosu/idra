What this view is

An operator asks what the cache costs to run, how close it runs to its limits, and what it does when something runs out (Chapter 3). The costs here are proved, in machine instructions per event, by the cost plane from the program; the failure paths are what the intent promises and, where noted, what the code does.

The stack

The firmware runs on the same stack before the image takes over; its share is assumed, not proved.

What is not bounded

  • Waiting for the lock. The cost plane counts one core's instructions, not time spent waiting for the other core to give a stripe back (S-1; docs/LEDGER.md #19).
  • Time. Bounds are in instructions. Latency is measured, not proved.
  • A whole pass of the main loop. It is bounded too, but over every connection at once: serve_pass at most 126,806,868 instructions, of which the timer scan tcp_poll is 104,969,100. No budget in the intent covers a pass; each step within it is under C-8's.
  • Boot. Boot functions wait on hardware in loops the proofs bound by a large count, so their worst cases (up to 25,742,006,574 instructions) say little about how long a boot takes, which was not measured.
