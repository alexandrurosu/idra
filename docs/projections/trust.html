What this view is

An auditor asks where the system trusts something it has not checked. This view answers from the build's records: what is proved and what is trusted, where data the program did not write enters it, which code may touch which device, and who can change the running system (Chapters 3, 6 and 9).

What is proved, what is trusted

Proved and validated

146 generated functions: every one proved against its contract (11,910 obligations), and 27,121 of the image's 28,200 instructions shown to do what the proved program does.

Trusted, hand-written

The other 1,079 instructions: the entry code, the 26-instruction stub that saves registers around the tick, and the routine that rewrites boundary sites. Reviewed, not proved.

Trusted tools

The checker and Z3, which prove the program; the validator's model of each instruction, tested against Arm's specification on 21,400 cases.

Assumed about the hardware

The network card computes outgoing checksums (N-9) and does not write a buffer after handing it over (N-10); both are stated in the intent, and a branch without them is kept.

Opaque and not contained

The UEFI firmware: it boots the image, runs on its stack before it takes over (32,768 bytes reserved, assumed) and is called at boot. The network card's and disk's own firmware. The image does not use an IOMMU to confine the devices' DMA, so Chapter 6's quarantine is not in place.

Chapter 6 sorts components by whether their behaviour can be known: generated and proved code is trusted completely; opaque code is contained. Here the proved part is the whole program, and the firmware is the opaque part, trusted rather than contained.

Who can change the running system

Between tenants and between cores

Tenants. A request reaches the cache only with a configured API key, and every key it passes to the cache begins with its tenant's digit (H-2): 12 obligations, all proved. The evidence files them under C-5; this view re-attributes them. No planted defect has tested this property yet. The API keys in the intent are test keys.

Cores. The two cores share the store under a lock with eight stripes. What one core may assume about the other is exactly the lock's invariant, and everything that runs while both run is proved to write only its own core's memory, memory a stripe it holds guards, or a device's: 191 race obligations (S-1).

The interrupt. The tick's handler writes only TICKS, nothing else writes it, and every read of it assumes nothing about its value: 7 interrupt obligations (N-11).
