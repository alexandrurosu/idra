What this view is

Intent is the only layer people write (Chapter 3). This page shows the cache's intent as written, split as Chapter 3 splits it: what the system does, and where it runs and what it assumes. Beside each clause is what checks it, taken from the build's records: the obligations proved for it, the cost bound, the tests, the assumptions, and the planted defects it caught. "Served by" lists the functions in the system graph that name the clause.

The evidence assigns each proof obligation to a clause by its kind of check, not by what it is about: all preconditions, postconditions, bounds, invariants and lifetimes count for C-5, for example. The intent-to-evidence projection shows the mapping.

C-1

C-4
Memory is divided into the size classes the workload declaration gives. When a class is full, its zombies are tried first: a hand of their own walks up to 32 slots and frees the first of at most 2 zombies no reply still refers to. Only if none is freed is an item of that class evicted to make room, chosen by CLOCK (second chance): an item read or written since the hand last passed is passed over once. Expired items go first; in the second half of a sweep any linked item may go. A sweep looks at no more than 32 slots and checks at most 2 zombies, so a set fails with SERVER_ERROR out of memory storing object only if those find nothing to free (for example, a small class whose every slot is a reply still in flight). A bucket of the table holds no two items with the same key hash and length: storing one evicts the other.
a reader holding 65,535 bytes of a deleted item still receives the original bytes (step 4) (tests/cachetest.py, tests/cachepin.py)

C-5
No item's memory is reused while a connection is still sending it or still receiving into it: an item that is deleted, replaced or evicted while a reply still refers to it is kept until no reply does. No item is read after it is freed or freed twice, every table cell names a linked item that names the cell back, and every reference a reply or a pending set holds names a live item. On EC2 a large value is sent from the item's own memory, which the network card reads after the frame is queued: such an item is also kept until the card has reported every frame that reads it sent, and every transmit descriptor that reads an item names a live one. On several cores, a core that may still send an item, or is filling it, pins it (writing its pin only while holding the stripe of the item's shard); an item is freed only when no core pins it. A pin for sending goes unless its core renews it (each shard every 16 ms, for every item there its replies and descriptors still name); that unused pins go is argued, not proved.

T-1
ARP, ping and TCP behave as in the network store (N-2, N-3, N-5, T-2, T-3, T-5): bad checksums are ignored, segments for no connection get a reset, unacknowledged data is retransmitted with a timeout doubling to 4 seconds, and a peer silent through 6 retransmissions is dropped. A peer that keeps answering with its window shut is not silent: it is probed with one byte each time the timer runs out, and kept. A peer's SYN options are honoured: its MSS bounds the segments sent to it (on EC2 up to 8,960 bytes, a jumbo frame), and its window scale, which the cache accepts with a shift of 0 for its own windows. Received data is acknowledged with the reply it causes, or after two full segments, or within 0.5 ms.

H-1
On TCP port 8080 the cache speaks the HTTP API of docs/FUSION.md: GET, PUT and DELETE on /item/{key}, over HTTP/1.1 with persistent connections and pipelining. The checks run in this order and the first that fails decides the reply: the target starts /item/ (else 404); X-Api-Key is one of the keys under [api] (else 401); the method is GET, PUT or DELETE (else 405); the key is 1-200 bytes of [A-Za-z0-9._~-], and a query appears only on a PUT and is then exactly ttl=N, N of 1-7 digits and at most 2,592,000 (else 400); a PUT's body has a length (not chunked: else 400, and the connection closes) of at most 65,536 bytes (else 413, and it closes). Then GET answers 200 with the value or 404; PUT stores the value, expiring N seconds later if a ttl is given, and answers 204, or 507 if no memory can be had; DELETE answers 204 or 404. Every reply to a well-formed HTTP/1.1 request is byte for byte what the split deployment's Go front end (fusion/api) sends, headers in the same order; requests that do not parse are answered 400 (505 for an HTTP version other than 1.1) and the connection closes. A body the request carries but the reply does not use is read past, or the connection closes if it is over 256 KiB. An item stored over HTTP is stored as a memcached set stores it, under the tenant's number and '/' before the key.
6,006 requests per deployment, replies byte for byte as the Go front end's (step 26) (tests/httpdiff.py)

Environment intent 9 clauses

Where it runs and what surrounds it: the devices it may touch and how far it trusts them, the cores, the one interrupt, the dynamic boundaries and who may switch them.

ClauseWhat it promisesChecked byServed by
S-1
The cache runs on every core it is built for (IDRA_CORES; the instance's two by default). Each core owns its connections and one queue pair of the network card, which spreads flows over the cores' receive queues (RSS). The items, the table and their bookkeeping are shared and split by key into shards (eight with several cores), each guarded by its own stripe of one lock: a shard is read or written only while its stripe is held, and a core holds one stripe at a time. Whatever a core holds outside the lock is its own: the build proves that everything that runs while several cores run writes only its core's own memory, memory a stripe it holds guards, or a device's. A stripe's invariant (its shard's shape, and what every core's pins promise for its items) holds whenever it is given back. Waiting for the lock is not bounded: the cost plane counts one core's instructions, not time spent waiting for the other (docs/LEDGER.md #19).

N-11
One interrupt is let in: the CPU's virtual timer, every 1 ms, through the interrupt controller (GICv3). Its handler only counts it (TICKS) and re-arms the timer; the main loop runs the connection timers and polls the console on each count; the other cores' loops read the same count. The handler writes nothing else, nothing else writes TICKS, and every read of TICKS assumes nothing about its value, so every other proof holds wherever the interrupt arrives. The entry stub that saves and restores the interrupted registers is hand-written and trusted, like the boot code. Without a GICv3 the loop counts passes instead.

N-12
Everything the cache does only to observe itself sits behind one of four dynamic boundaries: counters (get hits and misses, sets and full classes per class), sizes (the histogram of item sizes), profile (the clock time spent in each part of the main loop) and log (the access log, N-14). Each can be switched on and off while the cache runs. While a boundary is off, each of its sites is a single instruction that does nothing; switching it on rewrites those instructions into branches to the out-of-line code, and back. Every other guarantee holds for every setting of every boundary, at any moment: a site writes only its boundary's counters, allocates nothing, and leaves nothing behind that code outside the boundaries reads. Only the boot code, the serial console and the control port (N-13) switch boundaries. The routine that rewrites the sites is hand-written and trusted, like the boot code; the rewritten instructions are checked against LLVM like every other. On UEFI the firmware maps code read-only, so an image with dynamic boundaries asks it at boot to make its own code pages writable (and gives up that protection); if the firmware refuses, every boundary stays as booted and switching one answers ERROR. counters and sizes are on at boot, profile and log are off. On two cores each core keeps its own time profile, and a stats reply shows the profile of the core serving that connection; the counters and sizes are shared.

N-14
While the log boundary is on, the cache writes an access log to a local disk: a 64-byte record for every get (hit or miss), set, add, replace (stored, not stored, or out of memory) and delete (deleted or not found), with the core, a sequence number, the clock, the key's length, hash and first 32 bytes, and the value's length. The disk is the first NVMe disk whose block 0 carries the log's mark (written by tools/logdisk.py); no other disk is written, and if there is none the log cannot be switched on. The disk is driven by the cache's own NVMe driver, each core through its own queue, into its own part of the disk, kept as a ring of blocks. Best effort: serving never waits for the disk. Each core collects records in a ring in memory and hands the disk its finished blocks from its main loop, one write at a time; a record that finds the ring full is dropped and counted. While the log is on, a record reaches the disk within about 10 ms at low load and may lag by up to a ring (4 MiB per core on EC2) at high load; switching the log off stops it where it is, and what is still in memory is written when it is switched on again. No record is written over bytes the disk is still reading. Block 0 keeps a run number, raised at every boot and carried by every record.
records reach the disk; a full ring drops and counts, the request never waits (step 22) (tests/cachelog.py)

How the planted defects were refused

All 21 planted defects were refused before any image was built. 12 were refused with the clause they break and a counterexample. For 9, all about item lifetimes, the solver used up its work limit without proving the property; the build refuses whatever it cannot prove, so no image was built, but such a refusal shows the property was not proved, not that the checker found the fault.
