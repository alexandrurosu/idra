# Verifier ledger: where proofs shaped the code

The checker and the cost plane decide what code may ship. Where they cannot say
something true, the generated code routes around them, and the easy route is often
slower code. This ledger records every design choice the verifier forced, what it cost
at run time (measured where possible), and whether the verifier was fixed instead.

The point is the paper's: a verifier's precision is part of the design (chapter 12,
eleventh step). Constraints that come from intent (a budget a human chose) are listed
too, marked as such, because they look the same from the code's side.

| # | Choice the code made | What forced it | Runtime cost | Status |
|---|---|---|---|---|
| 1 | CLOCK eviction, not a true LRU list | Proving a doubly linked list well-formed at every step costs far more than CLOCK's short argument | Not measured; CLOCK is the usual approximation | Accepted by design (ch. 12, fourth step) |
| 2 | `stream_copy` copied 8 bytes or 1 per pass, redoing bookkeeping every pass, instead of one tight run per piece | The cost plane bounded each inner copy by a whole frame and multiplied by 32 pieces (1.6M > C-8's 1M) | Pipelined 399k vs what per-piece runs gave later (part of 839k) | **Fixed in the verifier**: amortised loop budgets (idra-check-5) |
| 3 | One command per connection per step of the main loop | C-8 bounds a step at 1M instructions and one command may be a 14-key get or 1 MiB | Pipelining behind at 32 connections (394k vs Redis 604k, same day, one client) | Partly addressed by #4 |
| 4 | Fast path serves 8 small gets per step, not 16 | Proved at ~33k per get (measured ~1.4k): ring writes charged twice (wrap split), every get charged the largest key and value; 16 proved at 979k, too close to 1M | **None measurable**: EC2 same day, 880.3k (8) vs 884.7k (16) at 64 connections, 914.7k vs 902.1k at 32, within spread | Closed: no runtime cost. Found while measuring: the binding bound was the QEMU build's (979k: virtio, software checksums); the EC2 image proves batch 16 at 718,821, inside 1M. So the batch can be set per board. Verifier fix: amortised byte budgets across calls, so a batch is sized by bytes copied, not by count |
| 5 | Multi-key get served 4 keys per step (KPS) | C-8, as #3 | Not measured | Open, same fix as #4 would apply |
| 6 | `sweep` finds up to two zombies, then reclaims them, instead of reclaiming as it walks | The attempt limit lived in a variable the cost plane cannot see (2.46M charged) | None: the same behaviour, stated in a shape the cost plane can count | Neutral restructure |
| 8 | Large values: at most 2 segments per connection step (MAXSEG), and a zombie freed only after a scan of all 4,096 reply pieces | C-8 (a step's sends are bounded); the lifetime proof (PI) is argued by that scan, not by reference counts | Measured: not the cause. 12 segments per step on EC2 (proved at 770k) changed nothing; the 16 KB gap was the card's per-queue transmit rate, closed by a second queue (44.5k) | Closed: segments per step raised per board; the zombie scan stays |
| 7 | (C-8's 1M itself) | Intent: caps how long one connection holds the loop (~0.4 ms), so a deep pipeline cannot starve other connections | The price of fairness; Redis pays none and wins deep pipelines | A human's setting, not a verifier limit |
| 9 | The 32 KB receive buffer compacted (moved its unread bytes to the front) when new bytes would run past its end | Not forced: the simple shape. But the cost plane charged the compaction to every frame: UEFI frame bound 82,137 -> 195,610 | Not measured (inside C-6's 1M) | **Fixed in the code**: the buffer is circular, nothing moves; UEFI frame bound 82,402. The fast path for queued gets declines a line that wraps the buffer's end (the general path takes it) |
| 10 | Copies split in two (a ring's wrap, a circular buffer's wrap) charged as two full copies; a reply's byte writes charged per call | Each loop had its own bound; budgets were per loop (#2) | Proved bounds roughly double the work; this is what held #4 at 8 | **Fixed in the verifier**: function budgets (idra-check-6): a function declares a byte budget its loops share, the cost plane charges it once. Applied to ring_put's callers, deliver, tcp_line, stream_copy |
| 11 | Zero-copy: a fragment's item checked live at run time when the frame is posted (`txq_postg`), and an item re-checked before its descriptor record is written | Z3 gave up (work limit) proving liveness carried from `stream_gather` through `tcp_send` to the driver | A few loads and compares per fragment; not separable in session 29 (zero-copy as a whole: pipelined -3%, mostly sends with no fragment) | Open: a verifier able to carry the liveness fact across the calls would remove the check. Also: freeing a zombie now scans the 2,048 descriptor records (C-8 conn_tick bound 821k -> 905k) |
| 12 | Two cores: the lock invariant (LI: the store, the table, both cores' pins) is stated only in functions that run holding the lock; elsewhere only this core's own invariants (pieces, pending sets, descriptors) | Z3 gave up (work limit) in tcp_in, tcp_rest, conn_serve and tcp_output when every function carried LI | None: specifications only | Accepted: it is also the honest statement (outside the lock the other core may change shared memory) |
| 13 | Small functions with their own contracts around single stores to the pins (`pin_item`, `fill_pin`, `raise_piece`, `raise_desc`, `drop_pin`; until session 31 `next_epoch`), and pin renewal split from clearing (`renew_pieces`, `renew_descs`, `clear_pins`) | One store inside a function carrying a dozen quantified invariants: Z3 gave up, or proved it under one term order and not another (the build's fixed hash seed) | None: all are inlined | Accepted; partly fixed in the verifier (#15) |
| 14 | Pins are 32-bit, so the epoch is too: after 2^32 epochs of 16 ms (2.2 years up) pins stop lapsing, and an item read on one core can then be freed only after that core reaps it (the behaviour before #16's fix) | Z3 proves the pin invariants over 8-, 16- or 32-bit elements in seconds; over 64-bit ones (signed or not) it used 2-20 GB per query and gave up. The first attempt paged the build machine to a halt | None until 2.2 years of uptime; then sets of large values may get out-of-memory replies under GET load | **Closed in the code** (session 31): there is no epoch any more. A send pin is one of two marks; repin renews the pins in use to the other mark and clears the rest, so nothing counts up. Why 64-bit elements defeat Z3 here is still not known |
| 15 | (Verifier) each obligation is tried first on weaker queries: the path condition's quantifier-free conjuncts (overflow, bounds, width, shift), then those plus the quantified conjuncts that mention only what the goal mentions; the full query only if both fail | Most of an obligation's cost was Z3 instantiating invariants about whole tables that the goal does not need | Build: Z3 work 9.67e9 -> 8.73e9 (-10%), 936 s -> 825 s, uncached, 8,492 obligations, same result | **Fixed in the verifier** (idra-check-7). Also: each Z3 worker capped at 1.5 GB (`IDRA_Z3_MB`), workers limited to what 80% of memory holds at the cap, so a proof that blows up is reported, not paged |
| 16 | Pins lapse: each core renews, every 16 ticks, the pins its pieces and descriptors still use, then moves its epoch on; a pin not renewed lapses within 32 ms (session 31: renews them to the other mark and clears the rest, one shard at a time, each shard every 16 ms) | Not the verifier: a design bug the verifier could not see. A pin set by a GET stayed until the same core reaped that zombie, so after a GET-heavy run nearly every large item was pinned by both cores and sets got out-of-memory replies (EC2, memtier's 2,000-byte prefill: stalled) | The renewal scans 4,096 pieces and 1,024 descriptors under the lock every 16 ms per core (~30k instructions); since session 31 every 2 ms, under one shard's stripe, plus that shard's pins (3,192 on QEMU, 44,323 on EC2) | Fixed in the code. Liveness (that a pin lapses) is argued here, not proved: the checker proves safety only |
| 17 | `fill_bytes` checks the copy's start is not negative (`dst < 0` -> copy nothing), beside the existing end check | The lower bound came from the slot invariant (a quantifier over all items): the 8-byte write bound cost Z3 1.1e8 | One compare per copy | Accepted (bound 1.1e8 -> 7.7e7) |
| 18 | Mutants `free_other_pinned`, `clear_without_renew` (was `epoch_without_renew`) and, since session 31, `wrong_shard` are refused only as "solver gave up", not with a counterexample (as are six older ones: `close_keeps_fill`, `free_large_now`, `free_while_card_reads`, `overwrite_cell`, `reclaim_without_scan`, `reference_small`) | Each breaks an invariant that Z3 can only refute through quantifiers | None | Open: a weak refusal; a counterexample would be stronger evidence. Session 31: `get_without_lock` now has counterexamples (mc_find requires the key's stripe held) |
| 19 | Time spent waiting for the other core's lock is not in any cost-plane bound | The cost plane counts instructions on one core; a spin's length depends on the other core | Not measured | Open, an intent gap: C-6 and C-8 bound work, not latency under contention |
| 20 | Shards: where an item's shard is known only from what this core recorded, it is checked at run time after taking that shard's stripe: a connection's pending set against FSH (`rx_drain`, `deliver`, `tcp_close`; outside it, nothing is copied), a piece's bytes by the shard their address falls in (`stream_copy`, virtio only), a set's key hashed again at commit (`mc_commit`), and the data copy clamped to the shard's data (`fill_bytes`) | Saying it in an invariant (FSH[c] names the shard of FILL[c]) puts a product of two array reads inside a quantifier every function carries; the DATA bound in `rx_drain` made Z3 give up (work limit) | A few compares per data delivery and per commit | Accepted; none of these can fail |
| 21 | `ctl_execute` states in its contract that it holds stripe 0 (the boundaries' state is stripe 0's) | A guarded region with no stripes belongs to stripe 0; the contract said only that some stripe is held | None: specifications only | Accepted |
| 22 | The access log's state (`LOGS`: tail, head, the end of the write in flight) is range-checked at run time where it is read, before a record is written or a write handed to the disk; `log_put`'s contract (the record lies outside the bytes the disk is reading) is then proved from those checks | An invariant on `LOGS` would have to be carried by every function that holds a log site (the request paths, ~40 functions with their callers) to be known at the sites; the checks give the same guarantee locally | A few compares per record and per pass, only while the log is on (off: a NOP) | Accepted: per-core state that only the log's code touches; an invariant scoped to a boundary's code would let the checker carry it instead |

Not compromises, but the verifier catching the code (for the record): the checksum loop
bounded by its 32 KB buffer instead of a frame (cost plane, before anything ran); a
regenerated layout with a negative class (the checker refused the partitions).
